## How the random check works

Each note is built from a pool of lines:

- link lines: with and without list markers (`- `, `* `, `+ `, `1. `, `3) `, `12. `, `-   `,
  `-<tab>`), numbered runs, task boxes (`[ ]`, `[x]`, `[X]`, with a tab or two spaces),
  indents (spaces, tabs, mixed), spaces or tabs after the link, 36 link forms (capital
  letters, no path, `%` codes, broken `%`, query, anchor, `(…)`, end slashes, end dots,
  other scripts);
- near link lines: each "no" row of rule 1 and more (link + text, two links, Markdown link,
  note link, quote, heading, `- 2. `, `[ ]` without a marker, `- [-] `, `<…>`, `-https://`,
  table cell, bold link);
- text lines, blank lines, lines of spaces or a tab, headings, `---` and `...` lines;
- frontmatter at the top (20% of notes; a quarter of them have no closing `---`), with YAML
  link lines, `...` and ```` ``` ```` inside;
- ```` ``` ```` and `~~~` fences, also after `- `, `- 1. `, `1. `, `- - `, with text after,
  closed by the same, a longer, a shorter or another fence, or not closed; lines that look
  like fences but are not (```` ```a``` ````, ```` ``` `x` ````, ```` `` ````, `> ``` `).

Line endings per note: all LF, all CRLF or mixed; the final line break is there or not
(so a last line can end in a lone `\r`); 10% of notes start with a byte order mark.

The oracle decides link lines (rule 1), skipped lines (rule 5) and blocks (rule 2) on its
own, step by step; it does not call `linkLine`, `LINK_LINE_RE` or `skippedLines`. Only the
key (`linkLine(…).key`) and `compareKeys` come from `src/sort.ts`, for the order check.

Checks per note:

1. only link lines change: every other line keeps its exact text and `\r` at its index; the
   line count stays; the byte order mark stays first;
2. every block holds the same links: the multiset of the moving parts (task box + link +
   spaces after it) is the same before and after;
3. the block is in stable key order (own insertion sort with `compareKeys`, not
   `Array.sort`);
4. each place keeps its start (indent + marker), stays a link line and keeps its own `\r`;
5. sorting twice changes nothing (`content`, `changed: false`, same `links`);
6. `lineChanges(before, after)` applied to the old text gives the sorted text; each change
   is one whole line from `ch` 0, and only on a link line;
7. `links` = the number of link lines outside the frontmatter and code blocks;
   `changed` = the text differs.

## Decisions

- The oracle is written from the rules, not copied from the code, so the check does not just
  repeat `src/sort.ts`.
- Checks 3, 4 (`\r`), 6 (shape) and 7 (`changed`) were added to the listed ones: without the
  order check a sort that does nothing would pass every listed check.
- "Same set of links" compares the moving parts (task box + link + end spaces), not only the
  web addresses: rule 4 says that whole part moves.
- 9 broken copies of `src/sort.ts` show that the check fails when a rule breaks (plan:
  "break each rule once").
- No-break space (U+00A0) is not in the pool and was not fixed. `probe.ts` shows:
  - before a link line or after a link: not a link line (rule 1 says spaces or tabs);
  - before an opening fence (`<nbsp>```): it opens a code block, so the links below stay;
  - after a closing fence (```` ```<nbsp> ````): it closes the code block, so the links below
    are sorted.

  The fence helpers use `trim()` / `trimStart()`, which also remove U+00A0. Rule 5 does not
  say which spaces count, the plan keeps `openingFence` / `closesFence` as they are, the owner
  wants the sort simple, and such lines are rare. Left as an open item: whether Obsidian
  treats a no-break space there as a space is not checked [Unverified].
- The examples check also stays in `/tmp`: the rule 1 table and the shared example are unit
  tests since Task 2.
