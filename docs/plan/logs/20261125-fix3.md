# Review fix 3: plain link lines changed the note's structure

- Plan: [docs/plan/done/link-sort.md](../done/link-sort.md)
- Date: 2026-11-25

## What was asked

Check the one major finding of the third code review against the code and fix it as the
user decided, with tests that fail when the rule breaks. Record the decision in the plan and
in SPEC.md "Sorting links". No commit.

Finding (`src/sort.ts`, link slot loop and fill): headings and tables were worked out from the
old order of lines only, then any link line could fill any link slot. A plain link line (no
list marker) that moved into a list-item slot could change what it is:

- above a `---` divider it became an underlined heading, and the divider was gone;
- right under a table (no blank line) it became a table row.

A second sort then counted fewer links.

## User decision

"Sort each kind apart" (2026-11-25, asked during this review): list-item link lines (text,
leading spaces and tabs skipped, starts with a list marker; `LIST_MARKER_RE`, so tasks too)
only fill the slots of list-item link lines; plain link lines only fill the slots of plain
link lines. Each group is sorted by the same key and order (stable, natural order). Notes
with only list-item links sort exactly as before. The pop-up count stays the total of all
link lines.

## What changed

- `src/sort.ts` — `sortLinkLines` puts each link line into one of two groups (`LinkGroup`:
  slots and lines): list items when `LIST_MARKER_RE` matches the text after `trimStart()`,
  else plain lines. Each group is sorted on its own and written back only into its own slots.
  `links` is the sum of both groups.
- `tests/sort_test.ts` — 4 new tests:
  - a note with both kinds (`- `, `- [ ]`, `1. `, an indented `  - `, two plain lines) sorts
    each kind among its own places (exact text);
  - the two `---` inputs: the plain line never moves above the divider (exact text);
  - the two table inputs: the plain line never moves under the table (exact text);
  - all four inputs: a second sort gives `changed: false` and the same `links` count.
- `tests/sort_test.ts` — 2 tests changed, because their input mixed one plain `#` link line
  with one list item, so under the new rule nothing moved: "a #tag line with a link is not a
  heading and gets sorted" and "a line with 7 # is not a heading, so its link gets sorted" now
  use two plain link lines. They still test their own rule (if the `#` line counted as a
  heading, only one link line would be left and nothing would move).
- `SPEC.md` — "Sorting links → Which lines move": the two kinds and how each one sorts;
  the pop-up count says "both kinds".
- `docs/plan/link-sort.md` — Solution Overview step 4, Key decisions ("Sort each kind
  apart"), Technical Details "Note sort" (two kinds, sort and write back per kind, `links`),
  Changes made during implementation (review fix 3).
- `docs/plan/logs/link-sort.md` — link 10.

## Decisions

- [decision] The main loop fills two groups (`listItems`, `plainLines`, one `LinkGroup` type)
  instead of filtering one list after the loop, so there are no extra array copies (review
  fix 1 removed copies).
- [decision] The two changed `#` tests use two plain link lines instead of more list items,
  because a `#` line is a plain line; with plain partners the test still fails when the `#`
  line counts as a heading.
- [decision] The mixed-kind test holds `1. `, `- [ ]` and an indented `  - ` item, so a rule
  that checks only `- ` or skips `trimStart()` fails it.
- [decision] Not changed: in Markdown, a numbered item that does not start at 1 (`2. …`) right
  under a text line belongs to that text. This was already so before this fix (the code
  counts every list marker as a list item), the finding does not touch it, and it is not
  checked in Obsidian; so it is not added to the known limits.
