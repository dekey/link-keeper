# Review fix 4: list markers stay in place, footnotes never move

- Plan: [docs/plan/done/link-sort.md](../done/link-sort.md)
- Date: 2026-11-25

## What was asked

Check the two major findings of the fourth code review against the code and fix them as the
user decided, with tests that fail when the rule breaks. Record the decision in the plan and
in SPEC.md "Sorting links". No commit.

1. `src/sort.ts` (link slot fill): list-item link lines moved whole, number included. A
   `1. 2. 3.` list came out as `2. 3. 1.` (Obsidian's reading view then numbers it from 2), a
   numbered item not starting at 1 right under a text line drops out of the list, and
   numbered lines landed in bullet lists (and the other way round).
2. `src/sort.ts` (`isFixedLine`, link line check): footnote definitions (`[^1]: https://…`)
   and link reference definitions (`[a]: https://…`) were plain link lines, so they swapped
   places with body lines. A body link line could land right under a footnote and become part
   of its text; a definition could move into the body.

## User decision

"Marker stays in place" (2026-11-25, asked during this review): for list-item link lines,
each list place (slot) keeps its own start — leading spaces and tabs plus the list marker
(`- `, `* `, `+ `, `1. `, `1) `, with the spaces after it). Only the rest of the line moves.
The task box (`[ ]`, `[x]`, any `[?] ` box right after the marker) moves with the link. So
lists keep their 1, 2, 3 numbers, their bullet or number kind and their nesting. The sort key
is taken from the moved part. Plain link lines still move whole and only fill plain places
("Sort each kind apart" stays).

Footnote fix (no question needed, it follows the rule that the note's structure never
changes): lines that start, after leading spaces, with `[^label]:` or `[label]:` never move.

## Confirmed

Reproduced with `deno eval` on the code before the fix:

| Input | Output before the fix |
| --- | --- |
| `# Reading list` / blank / `1. [[Zen and the Art]]` `2. [[Atomic Habits]]` `3. [[Deep Work]]` | `2. [[Atomic Habits]]` `3. [[Deep Work]]` `1. [[Zen and the Art]]` |
| `Books to read:` / `1. [[The Pragmatic Programmer]]` `2. [[Clean Code]]` `3. [[Atomic Habits]]` | `3. …` `2. …` `1. …` under the text line |
| `## Top` 1./2./3. web links, `## More` `- https://d.com/beta` | `2.`, `-`, `3.` under Top; `1.` under More |
| `# Article notes` … `Video: https://youtube.com/watch?v=x` / blank / `[^1]: …` `[^2]: …` | `[^1]:` under the body text, `Video:` under `[^2]:` |

Result: both CONFIRMED. No false positive.

After the fix the same inputs give `1. 2. 3.` in order, the `## Top` list stays numbered and
`## More` stays a bullet list, and the footnote note does not change (`links: 1`). A second
sort of each result gives `changed: false` and the same `links`.

## What changed

- `src/sort.ts`
  - `LIST_START_RE` (`/^\s*(?:[-*+]|\d+[.)])[ \t]+/`): the start of a list-item line.
  - `sortLinkLines`: each link line is cut into its start and the rest. The sort key comes
    from the rest. A slot is `{ line, start }`; slot *i* gets its own start + the sorted
    rest + its own line ending. Plain link lines have an empty start, so they move whole.
  - `DEFINITION_RE` (`/^\[[^\]]+\]:/`) in `isFixedLine`: footnote definitions and link
    reference definitions (leading spaces and tabs ignored) never move.
- `tests/sort_test.ts` — 6 new tests:
  - "a numbered list keeps its numbers 1, 2, 3 in order, only the links move" (reviewer
    input 1);
  - "a numbered list right under a text line still starts with 1 after the sort" (input 2);
  - "a numbered list stays numbered and a bullet list stays bulleted when links move between
    them" (input 3);
  - "a nested list keeps its indents, markers and the spaces after them in place" (`1) `,
    tab-indented `*   ` and `* `);
  - "footnote definitions with links stay in place while the other plain link lines are
    sorted" (reviewer input unchanged with `links: 1`; with a second plain link line in

  - "link reference definitions ([a]: address) stay in place while the other plain link

## Decisions

- [decision] `LIST_START_RE` starts with `^\s*`, the same characters `trimStart()` skips, so
  exactly the same lines count as list items as before (old check: `LIST_MARKER_RE` on the
  trimmed text).
- [decision] One `DEFINITION_RE` (`[label]:` at the start of the trimmed line) covers both
  footnote definitions (`[^1]:`) and link reference definitions (`[a]:`). Any number of
  leading spaces is ignored, like the heading and quote checks; it is the safe side (a line
  only stays).
- [decision] Only the definition line is fixed, not a text line right under a footnote (a
  "lazy" line that Markdown can count as part of the footnote). The user rule names the
  definition line; the lazy line is the same case as the lazy line under a quote, so it is a
  known limit in SPEC and the plan, not more code.
- [decision] The pop-up table cell "Note changed?" says "only the order of the links" (SPEC
  and plan), because a moved list-item line can now get another marker, so "only the order of
  lines" was no longer exact. The pop-up text itself does not change.
- [decision] The old task test was renamed and its input changed instead of adding one more
  task test, because "moves whole" is no longer the rule; the new input covers the user's
  `- [x]` into a `- ` place case and keeps the `[x]` / `[ ]` swap.
- [decision] The reviewer's `## Others` / `2. [[Yak]]` / `1. [[Zeta]]` case has no own test:
  the "numbered list stays numbered and a bullet list stays bulleted" test covers numbered
  lines landing in bullet places.
- [decision] `README.md` not changed: its feature line ("all other lines stay where they
  are") is still true.
