# Review fix 5: plain link lines keep the indent of their place

- Plan: [docs/plan/done/link-sort.md](../done/link-sort.md)
- Date: 2026-11-25

## What was asked

Check the major finding of the fifth code review against the code and fix it as decided, with
tests that fail when the rule breaks. Record the decision in the plan and in SPEC.md "Sorting
links". No commit.

`src/sort.ts` (`sortLinkLines`, link slot fill): a plain link line moved whole, with its
leading tab or spaces (its start was `""`). Inside a list item those spaces made it a line of
that item. When it landed at the left edge (under a heading, at the top of the note, after a
blank line outside a list), a tab or 4+ spaces turned it into an indented code block, so the
link showed as code and could not be clicked. The plain line that came back into the list
place lost its indent, so it joined the wrong item or split the list in two. A second sort
said `changed: false`, so the damage stayed. Obsidian indents nested lists with tabs, so a
link line under a nested item (`\t  https://…`) always has 4+ columns of indent.

## Decision

By the orchestrator, applying the user's own "Marker stays in place" rule to plain places
(the user's goal: the structure of the note never changes): every place (slot) keeps its own
start. For a list-item link line the start is the indent + marker + spaces after it (as
before). For a plain link line the start is its leading spaces and tabs (`/^[ \t]*/`). Only
the text after the start moves, and the sort key comes from that text. The kind (list item or
plain) comes from whether a list marker matched, not from the start being empty. The earlier
plan wording "Plain link lines still move whole" was the orchestrator's wording, not the
user's choice; it is replaced in the plan and in SPEC.md.

## Decisions

- [decision] Plain slots keep their own leading spaces and tabs (orchestrator, applying the
  user's "Marker stays in place" rule to plain places; reason: the user's goal is that the
  structure of the note never changes). Replaces "Plain link lines still move whole".
- [decision] The plain start uses `/^[ \t]*/` (only spaces and tabs), as decided, not
  `trimStart()`; other white space characters at the start are rare and move with the text.
- [decision] Three tests, not two: the third (reviewer input 3, `\tDocs: …`) checks that only
  the spaces and tabs stay and the text before the link moves; the first two would still pass
  if the start ran up to the link.
- [decision] `README.md` not changed: its feature line ("all other lines stay where they
  are") is still true.
