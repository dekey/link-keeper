## What was asked

## Decisions

- [deviation] `runInEditor` takes an options object `{ cursor?, failOnSetValue? }` as its 4th
  argument instead of a bare `cursor?`. The editor is made inside `runInEditor`, so the
  "fail on setValue" switch has to be passed in before the command runs.
- `setValue` keeps every text it got (`setValueCalls`), not only a count: tests check the
  call count and the exact text the command tried to write.
- `runInEditor` first asks the command if it shows (`checking = true`) and throws if not,
  like the command palette does. So every success test also proves the command shows for a
  Markdown note.
- `runInEditor` does not set the workspace's active file. A command that read
  `workspace.getActiveFile()` instead of `ctx.file` would see no file and fail the tests.
- The pop-up count is `result.links` (all link lines in the note), as in the plan's example
  ("Sorted 3 links" for 3 link lines). When lines move there are always 2 or more, so the
  text is always plural.
- Extra test beyond the plan list: a note with no links gets the "already in order" pop-up
  and no write (the plan's pop-up table row "0–1 link lines").
- The fake's `setCursor` accepts both forms of the real API (`setCursor(pos)` and
  `setCursor(line, ch)`).
